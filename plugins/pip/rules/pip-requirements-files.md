---
description: A requirements file is either hand-edited source or compiled output — read its header first, because edits to compiled output are erased by the next compile
condition:
  - "**/requirements.txt"
  - "**/requirements.in"
  - "**/requirements*.lock"
interruptMode: tool-only
---

Requirements files come in two kinds, and which this is decides whether you
may edit it:

- **`requirements.in` is source.** Hand-written, holding the loose constraints
  a human chose; in a pip-tools project the only place to change a dependency.
- **A compiled `requirements.txt` or `*.lock` is output.** `pip-compile`
  resolves the `.in` into a fully pinned transitive closure, so editing the
  output desynchronises the pins from the constraints and the next
  `pip-compile` overwrites your edit without comment.
- **The tell is the top of the file.** Compiled output opens with a header like
  `# This file is autogenerated by pip-compile with Python 3.x`, then
  `# To update, run:` and the exact command. Two signals corroborate it: every
  entry is pinned with `==` and carries a `# via <parent>` comment.
- **Header present:** edit the matching `.in`, re-run the command the header
  quotes, and commit both files together — change the constraint, never retype
  a pin in the output.
- **No header** — no `# via` annotations, loose or partial pins — means this is
  a plain hand-maintained `requirements.txt`, and editing it directly is
  exactly right. Read the first lines to decide; the filename alone tells you
  nothing.
